# Case study: correcting history without losing reproducibility

A measurement corrected tomorrow must replace yesterday's value without silently changing a report that a reader pinned yesterday. An out-of-order source file and a delete make this harder: file processing progress and business version order are separate clocks. Quarry solves this with an all-version identity registry, versioned latest-state tombstones, stable-key buckets and immutable manifests committed together with input checkpoints.

The central implementation choice is partition-local semantic identity. A global snapshot ID changes on every publication, so placing it in every node fingerprint would rebuild unrelated data. Instead, sorted authoritative key/version content produces a bucket identity, and child transformations consume that identity plus contract and code identity. Daily partial aggregates live in the same key bucket, so changing a row's day removes its previous contribution without coordinating date partitions.

The accepted standard run now supplies a committed-source scale check: five million originals plus 500,000 corrections, 100,000 deletes and 100 schema-addition upserts produced 4,900,100 live rows and 5,600,100 historical identities. The independent complete rebuild and a forced Parquet graph rebuild agreed exactly. Original ingestion/publication took 453.668 seconds (11,021.27 rows/s); peak process RSS was 312,631,296 bytes. See the [raw standard evidence](../../../docs/evidence/final/standard/quarry-3.14.8-benchmark-benchmark.json), [verification wrapper](../../../docs/evidence/final/standard/quarry-3.14.8.json) and [benchmark interpretation](BENCHMARKS.md). These are synthetic local results from clean commit `59443e2bcdfc6a1dd81f8334c108474eef2d3030`, with one costly measured run after a bounded 20,000-row warmup.

The broad standard updates did not save work through partition reuse: corrections/deletes touched all buckets and a schema change invalidated the graph globally, leaving 128 rewritten buckets and zero reused nodes in the final update publication. Three update ingestion/publication phases took 470.169 seconds, versus 121.067 seconds for one forced full graph rebuild from already stored current state, a ratio of 3.88356. Those operations do different work and the ratio is not evidence of an incremental speedup. The one-key demo demonstrates locality under a targeted correction; the standard run establishes correctness at the required size and exposes the cost of broad invalidation.

The most serious design defect found during implementation was GC ordering: unlinking files inside a not-yet-committed retention transaction could let crash recovery restore a catalog snapshot whose files had already disappeared. GC now commits snapshot deletion first, reacquires the writer lock, recomputes references, then unlinks only orphans. Reader-pin tests demonstrate the complementary retention boundary. Real process-death tests target the file/commit boundary, and an independent rebuild model checks version histories rather than reusing the production merge code.

A further regression tightened quality rules: repeated files bypass event parsing through source checkpoints, but a stronger dataset rule must still reject an invalid current dataset. Cached per-bucket summaries now participate in every publication's global quality reduction; `test_global_quality_rule_rejects_repeated_source` proves the checkpoint remains unchanged on rejection.

This is a local, one-writer analytical engine. Historical identities grow indefinitely; conservative stale pins may retain storage; global schema/code changes rebuild the graph; query ordering can require DuckDB spill. Future work could add explicit identity-retention migration, offline pin administration, richer partition-summary statistics and joins. Distributed lakehouse compatibility is deliberately outside its demonstrated contract.

A later integrity review found that checksums were recorded at publication but checked only by the explicit validation command. Replacing an immutable file with valid Parquet could therefore change a historical query or enter another manifest through reuse. File verification is now shared by queries, reuse and validation. A regression substitutes valid Parquet with a different measurement, checks that readers fail, and proves rejected reuse rolls back newly staged historical identities and source checkpoints. Recovery separately validates retained reference paths before removing snapshots or orphan files. Full-file hashing adds I/O; the historical benchmark results predate this change.

Recovery must also distinguish a valid empty dataset from damaged metadata. Format v1 always publishes three node files in every configured bucket, even when all files contain zero rows. A partial partition map could otherwise classify omitted live files as orphans. Shared structural validation now runs before retention commits, file reclamation, queries and publication. Empty/partial graph regressions preserve all snapshots and file bytes when recovery refuses the catalog; an actual zero-row snapshot remains valid and queryable.
