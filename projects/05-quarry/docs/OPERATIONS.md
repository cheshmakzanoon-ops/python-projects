# Operations

Install with `uv sync --locked --python 3.14.8` (tested default). Python 3.13.16 remains a fully tested compatibility path. Run format, lint, strict types, tests and build using the commands in [verification](VERIFICATION.md). CLI help lists `ingest`, `plan`, `build`, `validate`, `query`, `snapshots`, `lineage`, `recover`, `explain`, `gc`, `demo`, `benchmark` and `clean-demo`.

A dataset path must start empty or contain the `.quarry-owned` marker. Symlinks at owned storage paths are rejected. Source files are read only. The parser hashes the exact bytes consumed and compares them with the initial file hash, followed by an EOF rehash and another rehash immediately before manifest publication. This detects concurrent rewrites, including mutate-and-restore input histories that a simple before/after comparison misses. NDJSON record size defaults to 65,536 bytes. CSV headers and complete physical records share the same total byte bound. CSV requires one complete record per physical line; multiline quoted cells are explicitly rejected. Headers must contain unique declared event columns, and every row must match their width. Offsets are row ordinals rather than byte offsets.

`plan --source FILE` stages and validates in a transaction then always rolls back. It reports each bucket/node build versus reuse decision; it does not execute transformations or guarantee a future aggregate/content check will succeed. `build` publishes current state without new business records. `explain` returns the current manifest. `validate` pins its selected snapshot for the full size/SHA-256/schema/row-count and global daily-range checks. Its reported row count includes all three physical node types, not just live facts. Pinned queries verify the selected node's files before DuckDB execution; publication verifies every reused file. Content mismatch stops the operation. Neither validation nor queries repair damage: restore a consistent backup or the exact original immutable files. A failed input contract rolls back the complete batch and does not advance its source checkpoint.

`lineage` returns bounded ascending history with source hashes/offsets. Save the first response's `as_of_snapshot`, advance `--after-version` with `next_after_version`, and pass `--as-of-snapshot` on subsequent calls. Defaults are 1,000 entries per page, capped at 10,000. The cutoff freezes first-accepted history even if later ingestion inserts an obsolete version below the cursor; it remains usable after that materialized snapshot is reclaimed. Column dependencies come from `column_lineage_snapshot`, the current manifest, rather than the historical cutoff. See [API](API.md) for an executable pagination pattern.

Supply a JSON contract with `ingest --contract FILE` or `plan --contract FILE`. Fields are `{kind,nullable}` where kind is string, number, integer, boolean or json. Row quality uses optional finite minimum/maximum for value. Resource settings and row bounds must be integers; booleans and fractional values are rejected in both Python and JSON interfaces. Dataset quality uses min_rows/max_rows and validates the entire live state via per-bucket summaries, including repeated source deliveries and all-reuse plans. Policy-only changes validate without file rewrites. A nullable schema-only addition reuses normalized files and rebuilds typed facts and their daily descendants. Contract fields are copied into a read-only mapping at construction.

Only nullable additions evolve automatically. For an incompatible change, export a pinned snapshot, create a fresh dataset with the new contract/bucket configuration, explicitly transform/version events, verify facts and aggregates independently, then change the caller's dataset path. Migrating current live facts alone does not preserve historical conflict semantics: that requires the accepted historical identities too. No automated history migration or manual format-row reset is supplied.

Finite values can still overflow when summed within or across buckets. Publication rejects nonfinite global daily totals before catalog commit. Daily queries and validation also reject legacy nonfinite output, even with a one-row query limit. Correct the offending input/policy and retry; exact fact payloads remain exportable from an older invalid daily materialization. `DOUBLE` arithmetic remains approximate and can reject intermediate overflow even if a different evaluation order gives a finite mathematical result. Use a different explicitly designed numeric contract for exact financial totals.

Keep snapshots by default. `gc --retain N` explicitly retains at least the newest N snapshots and every registered reader pin; history registry and tombstones remain. `recover` removes unpublished files. It verifies the format version, every configured bucket, the complete normalized/facts/daily graph, node metadata and existing owned file paths before pruning snapshots or deleting orphans; an unsafe or missing reference stops reconciliation without deleting files. Every published snapshot, including a zero-row dataset, must contain all bucket/node entries. An empty or partial partition map is corruption, not permission to reclaim the missing entries' files. Recovery validates checksum/schema/count metadata structurally but does not compare it with file contents. Run both `recover` and `validate` after a crash. Pin tokens reside in the `pins` table. A crashed process may leave a stale pin; stop all readers before clearing a proven abandoned pin with SQLite. Never clear unknown pins during active reads.

For a backup, stop the writer, close all handles, and copy the complete owned directory after SQLite checkpointing (or use SQLite's backup API plus a consistent retained-file copy while the writer is stopped). Restore to a fresh directory, open it with Lakehouse, run recover and validate, then query known snapshots. Copying only catalog.sqlite while its WAL is live is not a safe backup.

Fault suite uses real child-process termination at after_files, before_commit and after_commit. `QUARRY_HARD_CRASH=1` makes the explicitly requested ingest fault terminate with exit 91; it has no effect on normal calls. These tests verify process-crash ordering, not every device/power-loss failure. Windows lacks the tested directory-fsync boundary and the benchmark uses Unix resource accounting; Linux is the required operations platform.

After interruption, reopen the dataset, run `recover`, `validate`, list retained snapshots and query a known result before resuming. Before-commit interruption leaves previous committed state plus possible orphan files. After-commit failure can report an error despite successful publication. Retry the identical source: source/event identities and results remain stable, though a replay can publish another metadata snapshot. Do not compensate for ambiguous progress by inventing new versions or editing checkpoints. Recovery never repairs altered committed bytes.

Use one application writer. Each `Lakehouse`/`Snapshot` and its SQLite connection belongs to the creating thread; concurrent readers need separate handles. Wrap the entire iteration in `with Snapshot(...)`. Closing a handle closes its active generators/DuckDB connections before removing the retention pin; a suspended generator then stops. Abandoning an iterator frees its engine while the still-open handle stays pinned. Explicit validation also pins while hashing, so concurrent GC cannot reclaim its files. Controlled test schedules cover validation during retention and a new publication between GC's catalog-retention and reference-recomputation transactions.

CSV parsing scopes and restores Python's process-global field limit while holding a local lock for each bounded record. This isolates interleaved Quarry readers; unrelated code changing that global outside the lock is not coordinated. Record/batch limits and DuckDB memory/thread/spill settings bound configured buffers and engine work, not process RSS. Leave disk capacity for exact catalog history, spill and unpublished files. Snapshot retention does not reclaim accepted identities, source checkpoints or tombstones.

Demo output requires an empty directory and a `.quarry-demo` marker. clean-demo rejects a missing marker, symlinks, or unknown top-level entries and removes only the generated run directory. Never place private files inside generated lake or benchmark subdirectories.
