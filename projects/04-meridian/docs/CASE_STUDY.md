# Auditable accounting under concurrency

A fictional equipment-rental business submits invoices and payments more than once when clients lose responses. Its operators need historical balances and reconciliation suggestions without letting duplicate HTTP requests or fuzzy references alter money. Meridian makes immutable postings the authority, serializes each tenant's commit sequence, and treats balances and statement proposals as reproducible derived state.

The central engineering choice is an enforceable database boundary. Python validates inputs, but direct SQL still cannot commit an unbalanced journal, mix account tenants/currencies, mutate a posted record, or append a later posting. One linked full reversal corrects history. A tenant row lock couples canonical idempotency and commit order. The cost is explicit: same-tenant writes contend, while independent tenants can write concurrently. This is more precise than claiming serializability from Django atomic().

Two meaningful defects emerged during verification. PostgreSQL interpreted a table alias named OLD as a trigger's OLD record, breaking reversal validation; the guard now uses an unambiguous alias and an incremental compatibility migration. More subtly, the assignment solver's initial ambiguity detector removed chosen edges and re-solved. Exhaustive Hypothesis enumeration found that adding an unmatched row to an unused right vertex at exactly the unmatched price can produce another optimum without removing an existing match. The corrected proof handles that case explicitly; a minimized 3×3 cost matrix is retained as a regression fixture.

A concurrency review also tightened direct SQL account locking from KEY SHARE to SHARE: a non-key currency update is compatible with KEY SHARE and could otherwise race insertion. Application row locks already prevented the ordinary API race; database enforcement needed the stronger lock as well. The account constraint is now protected at the database boundary.

Evidence includes real PostgreSQL opposing transfers, eight concurrent idempotent submits, aborted SQLSTATE retries, process death before commit, non-owner attempted mutations, sequence-prefix replay, competing approvals across runs, and snapshot restore. Tiny matching correctness uses independent exhaustive enumeration; larger workloads measure scale rather than claiming globally optimal reconciliation truth. Statement reference scoring is a review aid, not financial inference.

Limits: integer projection totals must fit bigint; tenant serialization bounds a single tenant's write rate; matching components cap at 32 rows/256 edges; only full reversals and explicit approve/reject are implemented. No end-user RLS, real bank execution, foreign exchange, regulatory certification, or production identity lifecycle is claimed. A production deployment would additionally need its own reviewed user lifecycle, observability policy, operational recovery objectives, and workload-specific capacity study.

The controlled-ambiguity ci development run measured approximately 63.2 same-tenant and 132.4 many-tenant journals/second with eight persistent clients, 1000 journals, 200 accounts and 500 statement rows. Five components were ambiguous and five statement rows remained unmatched as intended. This is a shared-machine development baseline, not final committed-snapshot performance or a production capacity promise. Native immutable-source standard measurements remain a coordinator gate.

Independent cross-project review found two defects beyond the original test model: an idempotency row could reference a different tenant's journal through direct SQL, and an account with statements but no postings could change currency or tenant. Those are now covered by a composite tenant/journal FK plus a defensive cache tenant check, and history-aware account guards synchronized with statement/run insertion locks. Legacy-corruption migration tests, raw SQL rejection, removed-membership authorization, and concurrent first-import/account-change tests preserve these fixes. The review also exposed the matching solver's finite infinity sentinel at an accepted cost of 10^30; explicit unreachable distances now preserve arbitrary Python integer costs, tested at 10^100.
