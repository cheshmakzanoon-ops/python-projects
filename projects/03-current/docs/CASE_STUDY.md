# Case study: making lateness replayable

A paused device source can hold the minimum watermark while another advances. Removing the paused source lets windows close; resuming with old readings can then revise or reject those readings. Saving source offsets alone cannot reproduce those decisions: the idle/resume interleaving is part of the input.

Current journals events and controls under one durable admission ordinal. The Python state machine owns watermark progression, heap-scheduled window close/expiration, aggregate revisions, and bounded interval joins. SQLite supplies the admission and checkpoint/outbox transactions. Sorting all input by event time would erase the recorded late-event policy, so that batch-only alternative was rejected.

The persistence boundary is checkpoint publication: a crash after staging must leave either the previous prefix or the complete new prefix, including its local results and outbox. The subprocess fault suite exits at four actual transaction phases and reopens the database. Another test loses admission acknowledgement after commit and proves its retry returns ordinal one. The independent sink test commits revision two before retrying revision one, then rejects conflicting revision-one payload reuse. Property tests derive expected dispositions and window/join results from the raw control trace without importing runtime algorithms.

Independent review also found a measurement defect. The benchmark sampled process RSS before executing its separate hot workload. That sample omitted any new high-water mark caused by the hot run. The regression in [test_benchmark_memory.py](../tests/unit/test_benchmark_memory.py) supplies a 100 KiB ordinary peak and a 1,000 KiB hot peak, and checks both the recorded bytes and sampling order after hot cleanup. Both CI/standard cases failed on the old ordering, reporting 102,400 bytes; moving the sample below hot execution and cleanup made them pass with 1,024,000 bytes. Run it with `uv run --locked pytest -q tests/unit/test_benchmark_memory.py`. The accepted clean compatibility checks include these cases: 32 tests pass on [Python 3.13](../../../docs/evidence/final/python313/current-3.13.16.json) and [Python 3.14](../../../docs/evidence/final/python314/current-3.14.8.json) at source `b3caa0e4594034ee8edf9ca05c3fd879d6fe18a2`.

The accepted [standard run](../../../docs/evidence/final/standard/current-3.14.8-benchmark-benchmark.json) tested committed source [ec1d0106](https://github.com/cheshmakzanoon-ops/python-projects/tree/ec1d0106df086a48923016c33199cfbda0aebbc0/projects/03-current) on Python 3.14.8 with SQLite WAL/FULL durability. One ordinary million-event run processed at 4,119.18 events/s; the separate million-event 50%-hot-key run processed at 3,450.22 events/s. Both compared all final results and dispositions with the independent raw-trace oracle. The ordinary run emitted 2,531,862 latest result rows and the hot run 4,389,302. These processing rates include runtime checkpoint publication; admission, final-checkpoint restore, export and batch-oracle reconciliation have separate costs. The complete benchmark command took 896.75 seconds, as recorded in the [execution report](../../../docs/evidence/final/standard/current-3.14.8.json).

The corrected process RSS high-water mark was 12,177,899,520 bytes, approximately 11.34 GiB, sampled after both workloads and hot cleanup. It covers the serial benchmark process, its full raw trace, millions of exported and reference result objects, Python allocations and native SQLite allocations. The four keyed asyncio workers share that process. This measurement cannot be attributed to the live engine alone or interpreted as a sum of independent worker processes. Runtime queue peaks were 53/95 records and operator-state peaks 4,584/2,905 for ordinary/hot workloads, but the full validation/export path still required substantial memory. This is the main measured operational cost revealed by the larger workload.

The next justified change is a bounded streaming export and independent validator that compares every logical result and disposition while placing large reference state in bounded batches or external storage. It must preserve the existing independent oracle and conflict checks; no such optimization is claimed here. Current remains a single-owner, fixed-topology runtime with retained ingress/delivery history, finite disk budgets and time-bucketed opposite-stream joins. These synthetic measurements establish reproducibility under their recorded inputs, not deployment capacity. Process termination tests do not simulate power loss or dishonest storage; distributed coordination and arbitrary HTTP exactly-once effects remain outside scope.


The subsequent core review found a semantic failure that both the earlier engine and its batch oracle shared: when A ended while B was idle, terminal infinity expired all state and rejected B when it resumed. A separate online model now tracks finished inputs explicitly and recomputes every prefix from accepted history. Its generated traces exposed that failure before the fix. The corrected trace preserves watermark 10, accepts B at 9 with lateness 2 and revises a sum from 3 to 7. This required checkpoint `current-3` and an operational rebuild path, because a finalized old checkpoint cannot prove that it never discarded resumed events.

That review also moved failure handling into explicit boundaries: stale checkpoint state is fenced inside the SQLite transaction, connection operations cannot share an accidental uncommitted transaction, and task cancellation waits for executor I/O to settle before returning control. Fault schedules compare every immutable revision against the online model, while a child-process test exercises the separate sink's commit-before-ack gap across two job namespaces.

The join algorithm previously scanned retained same-stream records even though none could match. A derived opposite-stream time-bucket index now merges at most three ingress-ordered bucket iterators lazily, preserving exact output order and stopping at staging backpressure. State slots are reserved before each allocation, including large sliding fanout. [Focused comparison evidence](BENCHMARKS.md#focused-join-comparison) records the changed lookup cost; genuine pair cardinality, full result export and independent reconciliation remain separate costs.
