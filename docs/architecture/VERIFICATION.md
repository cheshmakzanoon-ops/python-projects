# Verification method

Correctness evidence starts with a contract and a failure boundary. Passing tests are useful only to the extent that they distinguish the required behavior from a plausible broken implementation. The repository uses several complementary methods because no single suite establishes concurrency, recovery, numerical accuracy, and packaging at once.

## Independent references

| Domain | Useful independent reference | Common false assurance |
| --- | --- | --- |
| Workflow replay | Dependency closure and hand-derived transition traces | Replaying commands through the same reducer twice |
| Storage | Versioned dictionary histories, retained legacy fixtures | Comparing two adapters that use the same table lookup |
| Event time | Raw event/control prefixes with independently derived admission and results | An oracle copying the runtime's watermark policy |
| Accounting | Immutable-posting folds and exhaustive tiny matching graphs | Rebuilding balances from the projection being checked |
| Analytical pipelines | Complete rebuild after corrections/deletes and historical reads | Comparing only row counts or reusing cached aggregates |
| Static analysis | Trusted CPython fixture execution, lexical symbol references, concrete finite-state enumeration | Expected diagnostics generated by the analyzer itself |
| Search | Hand-calculated scores, visibility perturbations, held-out judgments | Self-authored relevance labels tuned with ranking changes |
| Model lifecycle | Frozen membership/artifact identities and offline/online comparison | A high score from overlapping temporal splits |
| Routing | Independent schedule/objective verifier and tiny exhaustive search | A solver validating its own cached costs |
| Audio | Predetermined signal ground truth and external transform/MIDI checks | Pitch error measured only on conveniently voiced outputs |

References have their own boundaries. A tiny exact routing instance proves that instance's objective, not a large heuristic's optimality. Trusted analyzer fixtures cover their authored semantics, not arbitrary reflection. Synthetic pitch accuracy says nothing by itself about real guitar recordings. Reviews state these limits next to results.

## Transaction and lifecycle schedules

Concurrency regressions coordinate a specific schedule with barriers, lock observation, or failpoints. Arbitrary sleeps cannot establish the ordering. Tests check both the visible result and the durable records that justify it.

For a write, identify authorization acquisition, reads/locks, mutation, commit, and acknowledgement. Then exercise failure or interference on either side of those points. Nested savepoints, retryable transaction aborts, stale owners, lost acknowledgements, and membership revocation are distinct cases. For resource lifetimes, keep a reader or threaded operation active while another operation requests close, cancellation, compaction, or collection.

A process-termination test leaves real durable files or database state for a fresh process to recover. A failed synchronization test establishes how the implementation handles uncertainty. Neither proves arbitrary controller/drive behavior under power loss. Restore tests include an actual supported old-format fixture; relabeling newly generated data as old is insufficient.

## Algorithmic work and resource budgets

Performance changes begin with an identified cost: history replays per transaction, blocks read per version lookup, states joined per CFG edge, records considered by a join, or rows materialized before a matching bound. Regression checks prefer deterministic work counts and correctness invariants over wall-clock thresholds.

Focused measurements retain the workload generator, baseline/source identity, parameters, warmups/repetitions, thread settings, hardware, outputs, and correctness checks. Five repetitions are the default; expensive diagnostics explicitly record exceptions. Concurrent-development timings are descriptive. A small focused improvement does not establish whole-product throughput or replace a standard profile.

Limits must constrain work before excessive allocation. Failure under a limit also needs a recovery story: whether the engine is reusable, whether publication occurred, which inputs are replayable, and whether an operator can safely change the limit. Historical high-water measurements are observability, not current live-state identity.

## Execution and evidence

The dispatcher isolates product/interpreter environments and per-check build outputs. It reads executed JUnit cases, verifies summary consistency, and refuses skipped, empty, stale, or incomplete results. Packaging checks install exactly the new wheel outside the source tree and run its demonstration.

Final evidence comes from a detached committed clone with inherited source/environment selectors removed. Source and shared-contract hashes are captured before and after execution. Each run retains command logs, JUnit, compact output records, and a file-hash inventory in `verification.json`. A partial invocation explicitly records its requested products/checks; it cannot stand in for the complete matrix.

Changes to shared tooling select every product on both declared patch versions in CI. Public integrations exercise separate installed environments. Documentation link/build checks establish navigability and rendering, not the truth of architectural claims. Those claims still require code and failure-boundary review.
